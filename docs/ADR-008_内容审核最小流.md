# ADR-008 内容审核最小流

状态：已采纳（2026-11-11）。范围：PRD P0 第 9 条"管理后台最小审核流：题目 `draft → reviewed → published`；撤回；记录审校员和版本"，
docs/03 的 P11、docs/07 §4。后端在 `services/api`，后台界面在 `apps/admin_web`。原始任务卡不在文件夹内，下面的验收标准由 docs 推导。

## 为什么先做这个

`docs/` 下有约 8.4 GB 的真题（ADR-007 末尾），要用它们就绕不开"自动切出来的题必须有人复核才能进入 published"（docs/07 §4）。
审核流是导入的前提，而且不依赖任何还没冻结的决策（Q-05 的"内容审校人"是谁，这里只提供机制，不替负责人决定）。

## 决策

**1. 状态流转与终态。** 四个决策：`approve`（draft → reviewed）、`reject`（draft / reviewed → draft，必须写原因）、
`publish`（reviewed → published）、`withdraw`（published → withdrawn，必须写原因）。`withdrawn` 是终态：要重新使用，
应该提交一个新版本（编辑与新版本见 ADR-009）。学生端只认 `published`（`question_service`），所以状态一变，学生可见性立刻跟着变。

**2. "提交者不能审自己的题"。** `approve` 和 `publish` 两步，`created_by` 等于操作人时返回 403 `self_review_forbidden`；
退回和下线不受限（撤回自己的东西不需要别人批准）。`created_by` 为空的题（已经发布的 17 道样题，没有"作者"）不受这条限制——
这是工程样题的特殊情况，真实导入的题必须带作者。这是 docs/07"提交内容的人不能作为唯一审校人"的最小实现；"独立"到什么程度
（同一个团队里的另一个人是否够）属于 Q-05，没有替负责人决定。

**3. 程序校验复用入库校验。** `approve` 与 `publish` 之前，把库里的题还原成样题种子的形状，交给 `content_seed.check_question`
（和样题入库同一套：结构、答案能通过自己的判定规则、提示与错项分析不泄题、解法条件齐全、图解参数在白名单内）。有问题返回 422
`content_checks_failed`，`details.problems` 逐条列出。"自编样题不得标称真题或原题"这一条只对工程样题生效，有授权来源的真题没有。
`publish` 再检查一次，是为了防止二审之后内容被改过。测试里确认了：全部 20 道样题（17 道已发布 + 3 道待审）都通过。

**4. 确认哪些解法。** `approve` 必须确认标准解法；快速解法要在 `solution_kinds` 里单独列出才算确认，没列出的保持"未审核"——
学生端对未审核的快速解法本来就不展示（docs/06 §3），所以漏勾不会造成泄漏，只是学生看不到快速解法。`reject` 撤销全部确认。
`publish` 要求标准解法已确认。

**5. 版本与并发。** 请求带 `expected_version`（审核人看到的题目版本），与当前版本不一致返回 409 `version_conflict`，防止批准自己没看到的内容；
状态不允许这个决策返回 409 `invalid_transition`（比如两个人同时二审同一道题，第二个人会收到它）。同一个幂等键只生效一次，
同键不同请求 409。版本检查先于状态检查，再依次是原因必填（422）、提交者限制（403）、程序校验（422）、解法确认（422）。

**6. 审计。** 每次决策写一行 `audit_logs`：谁（`actor_id`）、哪个操作、从哪个状态到哪个状态、哪个版本、原因、`request_id`；
不含任何学生数据。被拒绝的操作不留记录。审计表的 ID 是随机 UUID，同一道题的记录时间严格递增（相同时间加 1 毫秒），
否则审核历史会乱序——测试里一度因此时好时坏，是这样发现的。审核历史在题目详情里按时间顺序给出，没有单独的审计查询接口。

**7. 角色。** `users.role` 本来就有 `reviewer`、`admin`。本地身份 Mock 增加 `role` 查询参数（`student` 缺省，`reviewer`、`admin`），
只在本地环境、只接受回环地址，和原来一样；`parent` 要等监护授权方案（Q-03）。`reviewer` 与 `admin` 在审核上权限相同（`admin` 的
"管理配置/审计"还没有对应的接口）。学生调用审核接口、审核员调用学生接口都是 403，**角色检查先于任何资源查询和请求体校验**——
学生分不出"题不存在"和"没有权限"，也探测不到哪些题是草稿。为此给 17 个学生接口补声明了 403。

**8. 待审样题。** `seed/drafts/` 里 3 道新编的工程样题（数学、物理、化学各一），入库为 draft，作者是一个固定的占位 ID，
学生看不到，用来演示和测试审核流程。它们通过审核上线之后，学生端能正常作答、判定为"确定判定"，提示不泄题（有测试）。
和其他样题一样，没有经过学科审校。

**9. 契约。** `reviewQuestion` 从 `planned` 变成 `implemented`，新增 `listAdminQuestions`、`getAdminQuestion`。
题目的审校状态枚举叫 `QuestionStatus`——最初起名 `ReviewStatus`，和复测项已有的同名定义重复，YAML 默认让后写的悄悄覆盖先写的，
是复测相关的响应样例校验莫名其妙地失败才发现的。现在契约测试会拒绝任何重复的键（YAML 与两个 JSON 文件）。

**10. 后台技术选型。** Vue 3 + Vite + TypeScript（docs/02 要求 Vue 3）；路由用哈希模式，静态托管不需要重写规则；公式用 KaTeX，
只有 `$...$` 里的内容经过 KaTeX，其余文字走普通文本节点，不会被当成 HTML。接口类型由 `openapi-typescript` 从契约生成，
测试数据按这些类型写，契约一变编译就失败。TypeScript 固定在 5.9（`openapi-typescript` 的对等依赖要求 5.x）；jsdom 固定在 29
（31 要求 Node ≥ 22.22，开发机是 22.18）。登录只有"本地开发登录"，因为真实登录方式没定（Q-03）。

**11. 前端的幂等键。** 一个决策动作固定一个键；网络失败后重试同一个动作复用同一个键，内容变了（换了决策、改了备注）就换新键——
这样重试不会重复执行，也不会把另一个动作误当成重放。

## 没做、没验证的

- **只能审，不能改**——这一条已经在 ADR-009 补上：修改题目会产生新版本、旧版本留痕。
- 地区适用标记（`question_region_applicability.review_status`）与评分细则只能查看，不能在这里审核。
- 导入流程：从 `docs/` 的试卷文件产生 draft 题，还需要公式识别与 Q-05 的授权结论。
- 队列分页是 offset 游标；审计没有单独的查询页。
- 只在 Chrome 里用真实后端走过：二审、上线、下线、历史、学生端可见性。同一个人既不是作者又是审核人的情形在浏览器里走通；
  "提交者不能审自己的题"只在后端测试和组件测试里验证，没有在浏览器里用真实的作者账号走过。
- 无障碍只做了语义标签和键盘可达，没有用读屏软件走过；没有做窄屏适配以外的响应式。
- 测试：后端 `tests/api/test_admin_review.py` 40 项；后台 `apps/admin_web` 37 项；变异检查新增 5 条审核规则。
