# COST-307 旧入口发送前保守记账

2026-11-17。修复旧 `ModelGateway.invoke` 在调用尚未结束时工作器退出造成估算漏记的窗口。
本切片不关闭 COST-301 的持久 attempt、审计结算及恢复缺口。

## 缺陷与修复

旧逻辑首次发送前提交每日请求槽，但只在整个 invoke 的 `_finish` 中记录所有尝试的
累计估算。真实子进程在首轮发送或超时后的重试中退出，数据库只保留一次请求计数，
两个范围的估算费用仍为零。该缺陷已用测试适配器主动 `os._exit(23)` 复现。

现在每次正成本估算通过累计上限和暂停检查后，先调用既有
`BudgetStore.record_cost`，提交成功后才允许进入适配器。数据库实现仍使用平台→学生的
固定顺序，在同一短事务更新两个范围；没有新增表、迁移、价格或经营额度。
内存实现只保证进程内可见性，只有显式数据库存储才跨进程保留。
零成本不额外写估算，但每日请求槽与发送门控仍按原规则执行。

提交预算属于一次IO间隙；提交后重新检查共享暂停、候选授权/模型/路由、报价与请求上限。
若报价提高或配置变化使当前尝试不能发送，返回降级而不追加一次供应商调用。
已提交的保守估算不自动退款，也不因为适配器尚未被调用就冒称可以安全恢复所有并发状态。
因此费用桶可包含已提交但最终未发送的保守估算，不是实际账单。

结束时不再次收取已有估算，只在最终返回usage的估算高于已提交累计额时补正差额。
未知usage不按零退款，跨UTC日的重试继续记在首次准入日。响应usage仍只描述最后的返回，
不扩大为所有尝试的实际token或发票金额；失败/校验拒绝尝试的细粒度usage与逐attempt审计
仍需共享持久调用状态机补齐。

估算提交异常返回既有 `BUDGET_UNAVAILABLE`，不调用供应商、不回显存储异常。
配置任何每日金额上限时，旧invoke仍拒绝发送，不能用本切片替代正式持久金额预占。
默认外部模型开关、已配置的真实供应商、授权与留存门槛均未修改。

测试仅使用自编请求、脚本适配器和隔离测试库，没有调用真实模型、实际供应商账单或学生内容。
没有公开API字段/契约变更，单次持久调用路径继续使用其原有同事务预算与结算，未重复收费。

## 仍未完成

最终已知usage差额的崩溃恢复、真实账单对账、供应商侧查询与精确费用仍有缺口。
